# OmniPaxos Cross-Language Bindings Plan

This document outlines the strategy for exposing the OmniPaxos Rust core to other languages (Python and Go) via a standard C Foreign Function Interface (FFI).

## 1. Architecture Overview

OmniPaxos is designed as an I/O-free state machine. This architectural choice makes it highly amenable to FFI because the core library does not spawn threads or manage asynchronous runtimes; it simply takes inputs (messages, appends) and produces outputs (messages to send, decided entries).

The architecture will consist of three layers:
1.  **Rust Core**: The existing `omnipaxos` crate.
2.  **C-API Wrapper (`omnipaxos-c`)**: A new Rust crate exporting `#[no_mangle] extern "C"` functions, compiling to a dynamic library (`.so`, `.dylib`, `.dll`) and a static library (`.a`) with a C header file (`omnipaxos.h`).
3.  **Language Wrappers**: Python and Go libraries that link against the C-API and provide idiomatic interfaces.

## 2. Phase 1: Serialization Strategy

Before crossing the FFI boundary, we must define how data (Log Entries, Messages) is represented.
*   **Opaque Payloads**: Since OmniPaxos allows generic types `T`, the C-API must treat log entries as opaque byte arrays (e.g., `const uint8_t* data, size_t len`).
*   **Language-Agnostic RPC**: The user is responsible for serializing their language-specific objects (Python dicts, Go structs) into byte arrays (using Protobuf, JSON, or MessagePack) before passing them to the OmniPaxos C-API.

## 3. Phase 2: The C-API (`omnipaxos-c` crate)

Create a crate that wraps the generic `OmniPaxos` struct into an opaque pointer for C.

### Memory Management
*   Rust allocates the `OmniPaxos` instance and returns an opaque pointer (`void*`).
*   Provide explicit destructor functions (e.g., `omnipaxos_free(void* ptr)`) that the host language must call to avoid memory leaks.

### Core Interface Design
We will expose the following essential FFI functions (conceptual C signatures):

```c
// Initialization and destruction
void* omnipaxos_create(const OmniPaxosConfig* config);
void omnipaxos_free(void* op_ptr);

// Core operations
int omnipaxos_append(void* op_ptr, const uint8_t* data, size_t len);
uint64_t omnipaxos_get_decided_idx(void* op_ptr);

// Reading the log
// Requires a callback or returning a struct with an array of byte buffers
void omnipaxos_read_decided_suffix(void* op_ptr, uint64_t idx, DecidedEntriesCallback cb);

// Handling incoming/outgoing messages
int omnipaxos_handle_incoming(void* op_ptr, const uint8_t* msg_data, size_t msg_len);
void omnipaxos_get_outgoing_messages(void* op_ptr, OutgoingMessagesCallback cb);
```

## 4. Phase 3: Python Bindings (`omnipaxos-py`)

We will use Python's built-in `ctypes` or `cffi` to bind to the C dynamic library.

### Implementation Steps
1.  **Load the Library**: Use `ctypes.cdll.LoadLibrary` to load the compiled Rust `.so`/`.dylib`.
2.  **Define Argtypes/Restypes**: Map the C function signatures to Python `ctypes` (e.g., `c_void_p`, `c_char_p`).
3.  **Idiomatic Wrapper**: Create a Python `class OmniPaxos:` that abstracts away the raw pointers.
    *   In the `__init__`, call `omnipaxos_create`.
    *   In the `__del__`, call `omnipaxos_free` to ensure Rust memory is freed when the Python object is garbage collected.
4.  **Serialization Integration**: Allow the user to pass a serialization function to the Python class (e.g., `json.dumps().encode('utf-8')`) so they can seamlessly append Python dictionaries.

## 5. Phase 4: Go Bindings (`omnipaxos-go`)

We will use `cgo` to link against the static library (`.a`) and header file generated by the Rust crate.

### Implementation Steps
1.  **Cgo Directives**: Add `// #cgo LDFLAGS: -lomnipaxos_c` and `// #include "omnipaxos.h"` to the Go source.
2.  **Memory Pinning**: Go has a moving garbage collector. When passing Go byte slices to C, we must ensure they are pinned or copied. Since OmniPaxos takes ownership of appended entries, we should pass copies of the Go byte slices into the C-API to avoid GC issues.
3.  **Idiomatic Wrapper**: Create a Go `struct OmniPaxos` that holds the `unsafe.Pointer` to the Rust object.
4.  **Finalizer**: Use `runtime.SetFinalizer` on the Go struct to call `C.omnipaxos_free` when the Go object is garbage collected.

## 6. Open Questions & Design Decisions

> [!WARNING]
> Before beginning implementation, the following decisions need to be finalized:

1.  **Storage Layer FFI**: OmniPaxos relies on the `Storage` trait. How will the C-API handle storage?
    *   *Option A*: Provide an in-memory storage implementation inside the Rust C-API by default.
    *   *Option B*: Provide a C-callback interface so the host language (Python/Go) can implement the storage layer (e.g., writing to a local SQLite DB in Python). (This is significantly more complex due to FFI callback overhead).
2.  **Network Layer**: Similar to storage, since OmniPaxos does not handle its own networking, the host language is responsible for taking the output of `omnipaxos_get_outgoing_messages` and sending it over the wire. The FFI must efficiently serialize internal OmniPaxos `Message` structs into byte arrays that the host language can route.
